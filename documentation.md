# Dorm Verification Bot – Documentation

## 1. Общее описание

Dorm Verification Bot — это Telegram‑бот, который автоматизирует процесс проверки заявок в чат общежития.  
Он помогает администраторам убедиться, что в чат попадают только реальные жители общаги, и избавляет от ручной переписки с каждым новым участником.

Основные задачи:

- автоматическая обработка join‑request’ов в группу;
- проверка пользователя через ЛС бота (ФИО + подтверждающие документы);
- пересылка анкеты в админский чат без хранения файлов у себя;
- управление доступом через белый/чёрный списки.

## 2. Архитектурное решение

### 2.1. Общая схема

```text
Пользователь → Группа общаги → Join Request
                        ↓
                Dorm Verification Bot
                        ↓
ЛС с пользователем ←→ Бот ←→ PostgreSQL (users/whitelist/blacklist)
                        ↓
                Админский чат (анкеты, кнопки)
```

- **Telegram Bot API** – источник апдейтов (`chat_join_request`, сообщения, callback‑query).
- **Go‑приложение** – бот, который:
    - принимает апдейты;
    - управляет состояниями диалогов;
    - читает/пишет данные в PostgreSQL.
- **PostgreSQL** – хранит:
    - пользователей и их статус;
    - белый и чёрный списки.
- **Docker + docker‑compose** – упаковка и запуск бота и БД.
- **systemd‑юнит** – автозапуск и перезапуск на сервере.

### 2.2. Структура проекта

```text
dorm-bot/
├── cmd/
│   └── bot/
│       └── main.go          # входная точка: загрузка конфига, БД, запуск бота
├── internal/
│   ├── config/
│   │   └── config.go        # чтение env, формирование структуры Config
│   ├── db/

│   │   └── migrations.sql   # SQL-миграции: users, whitelist, blacklist
│   ├── models/

```

### 2.3. Ключевые элементы архитектуры

#### 2.3.1. StateManager

Хранит состояние диалогов **по пользователям**:

- `StateWaitFullName` – ждём ФИО;
- `StateWaitDocs` – ждём документы (фото/кружки);
- `StateAdminWaitRejectReason` – ждём от админа причину отказа.

В `Session` храним:

- `UserID`, `GroupID`;
- `FullName`;
- `MediaMsgIDs` – ID всех сообщений с медиа в ЛС пользователя;
- вспомогательные поля (например, `RejectTargetUserID` для администраторского отказа).

StateManager использует `sync.RWMutex` и `map[int64]*Session`, что позволяет безопасно работать с несколькими пользователями одновременно.

#### 2.3.2. Store (models)

Инкапсулирует работу с базой:

- проверка списков:
    - `IsWhitelisted(ctx, telegramID)`;
    - `IsBlacklisted(ctx, telegramID)`;
- операции со списками:
    - `AddToWhitelist`, `RemoveFromWhitelist`;
    - `AddToBlacklist`, `RemoveFromBlacklist`;
- операции с пользователями:
    - `UpsertUser` – создать/обновить пользователя по `telegram_id`;
    - `UpdateUserStatus` – обновить статус (`pending`, `approved`, `rejected`, `blocked`, `unverified`);
- получение статуса списков:
    - `GetListStatus(ctx, telegramID)` → `whitelisted` / `blacklisted` / `unverified`.

#### 2.3.3. Bot (handlers)

Пакет `internal/bot` отвечает за:

- получение апдейтов от Telegram (`GetUpdatesChan`);
- обработку:
    - join‑request;
    - личных сообщений;
    - callback‑query;
- вызовы методов Telegram Bot API (`ApproveChatJoinRequest`, raw `declineChatJoinRequest`, пересылка сообщений).

Основной тип:

```go
type Bot struct {
    api         *tgbotapi.BotAPI
    state       *StateManager
    store       *models.Store
    adminChatID int64
    groupID     int64
}
```

## 3. Потоки работы (user flow)

### 3.1. Новый пользователь

1. Пользователь жмёт «Подать заявку» в группе.
2. Бот получает `ChatJoinRequest`.
3. Бот проверяет:
    - если пользователь в **чёрном списке** → сразу отклоняет join‑request;
    - если в **белом списке** → сразу одобряет и добавляет в группу;
    - иначе → запускает диалог.

4. Бот пишет пользователю в ЛС:
    - запрос ФИО (`StateWaitFullName`);
    - после получения ФИО → сохранение в БД и переход в `StateWaitDocs`.

5. В `StateWaitDocs` пользователь шлёт фото/кружки.  
   Бот:
    - накапливает `MediaMsgIDs`;
    - показывает кнопку «✅ Готово, отправить админам».

6. После нажатия кнопки:
    - бот формирует шапку анкеты (ФИО, ссылка на профиль, ID, группа);
    - пересылает все накопленные сообщения с медиа;
    - отправляет в админский чат inline‑кнопки «Одобрить» / «Отклонить»;
    - сообщает пользователю, что анкета ушла на проверку.

### 3.2. Администратор

В админском чате под анкетой:

- «✅ Одобрить»:
    - одобряет join‑request;
    - добавляет пользователя в whitelist;
    - обновляет статус пользователя на `approved`;
    - шлёт пользователю приветственное сообщение.

- «❌ Отклонить» (если включён запрос причины):
    - бот просит админа в ЛС написать причину;
    - админ пишет текст;
    - бот отклоняет join‑request;
    - сохраняет причину (например, в blacklist или лог);
    - шлёт пользователю отказ с текстом причины.

## 4. Команды и поведение бота

### 4.1. Команды для обычных пользователей

Все команды обрабатываются в ЛС с ботом.

- `/start`  
  Поясняет, что бот занимается проверкой заявок и нужно просто подать заявку в группу, после чего бот сам напишет.

- `/help`  
  Кратко описывает процесс: заявка → ФИО → документы → проверка админами.

### 4.2. Команды для администраторов

Админ определяется функцией `isAdmin(userID)` (в базовом варианте – через `ADMIN_CHAT_ID`, при необходимости можно расширить до списка ID).

- `/start`  
  Описание возможностей бота для админа и перечень команд.

- `/help`  
  Детальное описание процесса, роли whitelist/blacklist и inline‑кнопок.

- `/status <telegram_id>`  
  Возвращает статуса списков:
    - `whitelisted`
    - `blacklisted`
    - `unverified`

  Использует `GetListStatus` из `Store`.

- `/whitelist_add <telegram_id>`  
  Добавляет пользователя в белый список.  
  Следующие заявки будут автоматически одобряться.

- `/whitelist_remove <telegram_id>`  
  Удаляет пользователя из белого списка.

- `/blacklist_add <telegram_id> [причина]`  
  Добавляет пользователя в чёрный список.  
  Все последующие заявки из этой учётки отклоняются без диалога.

- `/blacklist_remove <telegram_id>`  
  Удаляет пользователя из чёрного списка.

## 5. Краткое описание основных файлов кода

### 5.1. `cmd/bot/main.go`

- загружает конфиг (`config.Load()` из env);
- устанавливает подключение к БД (`db.Connect`);
- применяет миграции (`migrations.sql`);
- создаёт `Store` и Telegram‑клиент (`tgbotapi.NewBotAPI`);
- инициализирует `Bot` и вызывает `Run()`.

По сути, это точка входа, которая собирает все зависимости и запускает главный цикл обработки апдейтов.

### 5.2. `internal/config/config.go`

Читает конфигурацию из `.env` / переменных окружения:

- `BOT_TOKEN`
- `ADMIN_CHAT_ID`
- `GROUP_ID`
- `DATABASE_URL`

Преобразует их в удобную структуру `Config` с нужными типами (например, `int64` для chat_id).

### 5.3. `internal/db/db.go`

Создаёт `*sql.DB` на основе `DATABASE_URL`, проверяет подключение (`Ping`).  
Используется во всём проекте через `Store`.

### 5.4. `internal/db/migrations.sql`

Содержит SQL‑скрипт, который создаёт:

- `users` – статусы пользователей;
- `whitelist` – белый список;
- `blacklist` – чёрный список с причиной.

Этот файл применяется при запуске бота.

### 5.5. `internal/models/models.go`

Определяет:

- тип `UserStatus` и возможные значения (`pending`, `approved`, `rejected`, `blocked`, `unverified`);
- тип `Store` (обёртка над `*sql.DB`);
- методы:
    - `IsWhitelisted`, `IsBlacklisted`;
    - `AddToWhitelist`, `RemoveFromWhitelist`;
    - `AddToBlacklist`, `RemoveFromBlacklist`;
    - `UpsertUser`, `UpdateUserStatus`;
    - `GetListStatus` – простой статус списков.

Задача файла – изолировать SQL‑логику от остального кода.

### 5.6. `internal/bot/state.go`

Определяет:

- `UserState` – состояние диалога;
- `Session` – данные конкретной сессии (ФИО, IDs сообщений, служебные поля);
- `StateManager` – concurrent‑safe хранилище состояний и сессий.

Используется в `handlers.go` для диалогов с пользователями и админами.

### 5.7. `internal/bot/handlers.go`

Содержит основную логику бота:

- `Run()` – главный цикл обработки апдейтов (`ChatJoinRequest`, `Message`, `CallbackQuery`);
- `handleJoinRequest` – логика обработки join‑request:
    - проверка whitelist/blacklist;
    - автоматическое одобрение/отклонение;
    - запуск диалога.
- `handleMessage` – маршрутизация входящих сообщений в ЛС:
    - если это команда → `handleCommand`;
    - иначе по текущему состоянию (`handleFullName`, `handleDocs`, `handleAdminRejectReason` и т.д.).
- `handleCallback` – обработка inline‑кнопок:
    - «Готово, отправить админам» → отправка анкеты и медиа;
    - «Одобрить» / «Отклонить» → join‑request approve/decline.
- `handleCommand` – реализация всех команд `/start`, `/help`, `/status`, `/whitelist_*`, `/blacklist_*`.
- `declineJoinRequest` – низкоуровневый вызов `declineChatJoinRequest` через raw API запроса, так как в `tgbotapi` нет готовой структуры.

## 6. Инструкция для пользователей

### 6.1. Обычный житель общаги

1. Открой чат общежития.
2. Нажми «Подать заявку».
3. Жди, пока тебе напишет бот:
    - отправь ФИО;
    - отправь фото/кружки с документами (несколько сообщений);
    - нажми кнопку «✅ Готово, отправить админам».
4. Жди решения:
    - при одобрении бот напишет, что тебя добавили в чат;
    - при отказе бот пришлёт причину (если админ указал её).

### 6.2. Администратор чата

1. Следи за админским чатом, куда бот шлёт анкеты.
2. Под каждой анкетой:
    - нажми «✅ Одобрить», если всё ок:
        - пользователь попадёт в группу;
        - добавится в whitelist;
        - в следующий раз будет проходить автоматически.
    - нажми «❌ Отклонить», если не ок:
        - бот отклонит заявку;
        - (опционально) попросит причину и отправит её пользователю.

3. Управляй списками и статусами через команды в ЛС:

- `/status <telegram_id>`
- `/whitelist_add <telegram_id>`
- `/whitelist_remove <telegram_id>`
- `/blacklist_add <telegram_id> [причина]`
- `/blacklist_remove <telegram_id>`
